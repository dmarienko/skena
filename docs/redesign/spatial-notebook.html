Spatial Notebook

Notebook ergonomics for the code flow; the free 2-D canvas for everything else — docs, parallel exploration, spatial memory. One model that ends the 90%-of-the-time-spent-fixing-placement problem: the tool lays out code, you keep the freedom for the rest.

01

The slot grid

Every node occupies whole slots. A slot is portrait (golden: h ≈ 1.61 × w). Move and resize snap to whole slots, so spacing is uniform by construction and you resize in visible steps, never pixels.

slot = w × 1.61w · nodes span N slots

PROPOSAL — confirm the numbers

The grid substrate already shipped: constants.ts holds one GRID + a per-type size table, and drag/resize snap to it. v1 formalizes it as portrait slots and makes per-type widths slot-counts.

Resize = whole slots

w/W already step one grid cell from the right edge; e/E one cell from the bottom. v1: those steps are slots.

OPEN — code auto-height

A code cell grows with its content up to ~100 lines. Chunky per-slot (gains a whole slot when text overflows) vs. smooth-while-typing then snap on blur. I lean chunky — matches the "big steps" feel.

02

A bounded canvas

No infinite void in every direction. The top-left is a real origin — nothing pans, jumps, or lands above or left of it. The canvas grows only right and down, as far as the work needs — giving the spatial-notebook a stable "top of the document" to anchor memory and navigation.

PROPOSAL — hard top-left origin

Pan clamps at the corner; nodes never take negative coordinates. A one-slot gutter keeps the first node off the very edge.

Existing canvases migrate

Your current canvases live in negative space — live-slippage has nodes near x = −5700. On open they're normalized: the whole canvas shifts so its min corner sits at the origin. No hand-work.

UNLOCKS — a Home key

Home jumps to the origin. The top of the canvas is now a real place you can always return to.

04

Inside a section — the layout engine

Inside a section the flow runs like your H3 example: cells run down (the sequence), each cell's output attaches to its right, and a fork opens a new column (left or right); docs and notes sit wherever they help. The engine keeps it packed — grid-aligned sizes, a visible gap everywhere, never overlapping, reflowing on every insert, drag or resize.

  1. Never overlap. Two nodes can't occupy the same space, ever.
  2. Always a gap — at least one grid cell between any two nodes, so you can see the connections through it.
  3. Insert / remove between reflows the rest; nothing is left overlapping.
  4. Drag & drop to a new spot — the layout recomputes to fit it.
  5. Resize a node — neighbors reflow and the section grows taller if needed.
  6. Code cell starts at the constants.ts default, then grows with its lines up to a max height and shrinks back down (Jupyter-style).
  7. Output cell sticks to its code (moves with it); no output → no cell; starts wider than a code cell and grows to a max width; resizing still obeys 1–5.

05

Connections

Edges are typed, and each one is drawn separately — never bundled into a single line — routed at right angles through the guaranteed gaps so every connection stays traceable. Color says what a connection means.

typed · orthogonal · routed through the gaps
code → code · sequence code → output context · varies

Every connection is visible

Parallel edges are offset, not merged; the router uses the 1-cell channels between nodes as lanes, so you can always trace a line end to end.

Typed & colored

  • code → code — records the sequence (down-flow + fork). Optional: a cell doesn't need it to run.
  • code → output — the stuck-output edge.
  • context — the paragraph-anchored links: paragraph → node or paragraph → paragraph. Colour = link group.

Sequence and output edges are drawn by the engine; context edges are the ones you draw.

Follow a connection

Beyond spatial h/j/k/l, follow an edge to jump straight to what it connects — the graph you drew becomes navigable.

PHASE 2 — semantic links from crtx

Anchor a link to a paragraph, follow by click. Later, pull crtx-server's embedding links in: each paragraph already carries related-passage in/out edges from the vector DB — surfaced here as suggested context connections.

RESOLVED — execution ≠ connection

Drop a lone code cell into a section and run it — no fork, no sequence edge needed. It runs on the section's kernel regardless. Edges only record the sequence; they never bind execution — today's kernel-edge (BFS) binding goes away.

Run order. Running a cell walks its connections backward and runs only the cells it's connected to, skipping any already run. Nothing off that backward path is touched — an unconnected branch, or a standalone cell, isn't pulled in. That's the old run-with-upstream, now over the fork tree instead of a path to a kernel.

run E5 → E1 (ok · skip) · E3 (runs) · E5

└▸E3 ▶ runsE5 ▶ target
E1 already ok → skipped · E3 was unrun → runs first · then E5 · the other branch (E2, E4) stays untouched · one shared section kernel

Keyboard

  • o / Alt+X j — next cell below, continue the sequence.
  • Alt+X l — fork right, a new column beyond the output.
  • Alt+X h — fork left (a second branch).
  • No k — you can't add above; the flow only grows down and out.

Insert on an edge

Hover any edge → a + knob appears → click to drop a node between the two it connects. The edge splits and the rest reflows — never overlapping.

RESOLVED — fork either side

h forks left, l forks right — branch on either side. And non-code nodes aren't pinned left: drop a doc or note anywhere in the section you need it.

07

Sections stack down the canvas

The canvas is a vertical stack of sections from the origin down. New sections append at the bottom — never inserted above or between. Many sections can share one kernel; a shared kernel means a shared color, so the tint groups by kernel and the title + time tell them apart.

Everything belongs to a section. There are no free-floating nodes — code, output, docs, notes each live in a section, and a code cell runs on that section's kernel.

Append-only

You add a section at the bottom; you can't wedge one above or between. The stack is the timeline — top is oldest, bottom is newest, each stamped with its creation time.

Same kernel → same color

The two quantkit sections share a kernel, so they share the green tint. Kernels are a shared resource; a section just points at one.

Fold, delete — title survives

Fold a section to its title bar (#S4 above); delete one outright. The title bar always survives a fold, so the map stays readable.

Three ways to add a section

  • the New section button at the bottom of the stack
  • an MCP command, so the AI companion can add one
  • drop a document on free canvas → it becomes a new section

Moving between sections

Drag & drop, or cut / paste, a node into another section. A code node adopts the new section's kernel; its output moves with it.

OPEN — cross-section edges

Context links can span sections (a note → a doc elsewhere) — keep them. A sequence (code→code) edge across sections would make run-with-upstream cross kernels, so it likely breaks on the move. Your call.

Fixes pains #2 and #5

The complaint was "I can't tell which part is which from the bird view, and I lose my place." A constant-size label per section is the whole fix — you read the map at any zoom.

Cell count on the label

Each section tag can carry its kernel + a live cell count, so the map is also a table of contents.

Drawn outside the zoom transform (constant px), unlike the cells. Same technique as the zoom-invariant borders skena already ships.

10

Navigation with guardrails

Hard invariant: spatial navigation only pans, never rescales. The zoom level stays exactly where you left it until you deliberately zoom in or out — no focus, jump, follow, search, Home or cross-section move ever changes it. This is the rule that ends the "eyes bleeding".

hjkl

Pan-only movement

Focus moves node-to-node; the camera pans the minimum to bring it in view. Zoom never changes. (Today focus/cross-jumps still zoom — that stops.)

The section minimap

A git-tree-style rail down the left edge — one knob per section, colored by its kernel, with its time and title. Toggle on/off; click a knob to jump. Consecutive same-kernel sections read as one colored lane; a kernel change switches color, like a branch.

A git graph, for research

Colored knobs on a spine, each row a section: color = kernel, plus #S · title · time. Same-kernel runs share a lane; a kernel switch changes color at that knob.

The navigation hub

Click a knob to jump; the current section is highlighted. Pulls everything from panel 07 — Ctrl+U/Ctrl+D, #S3, jump-by-time — into one visible list.

Folded reads hollow

A folded section (#S4) shows a hollow knob, so the map tells you what's collapsed at a glance.

PROPOSAL — left rail, toggleable

Remembered per canvas; a hotkey toggles it. Distinct from the bird's-eye (the canvas zoomed out) — the minimap is a compact outline that stays the same at any zoom.
